## Overview

This chapter focuses on understanding the dynamic aspects of a system, going beyond static structures. It emphasises how objects interact and collaborate to fulfil system functionalities. 

It aims to equip readers with the fundamental concepts and notations for behavioural modelling using UML diagrams, providing a foundation for understanding and representing the dynamic aspects of software systems.

A model of software is designed in a language called UML. The classification of UML diagrams is shown in the diagram below. We can divide it into three parts. 

1. **Structural Classification:** 
It describes the relationship between an object and another object; while the classifier describes the Static View, Use Case View, and Implementation View. 
2. **Dynamic Behavior:** 
It depicts the behaviour of the system with time. Behaviour can change with time and can be represented using State Machine, Activity and Interaction Diagrams. 
3. **Model Management:**
This is the third part that describes the organisation in a hierarchical structure.

**Key Concepts:**

- **Behavioural Modelling:** This modelling technique illustrates the internal workings of a system, highlighting the interactions between objects rather than their static structure. This approach aids in comprehending the system's functionality without dictating specific implementation details.
- **Interactions:** In a dynamic system, objects communicate by exchanging messages. Interactions, encompassing these message exchanges, demonstrate how objects collaborate to achieve specific objectives.
    - **Objects:** Fundamental building blocks representing system entities.
    - **Actions:** Discrete steps within an operation, signifying the progression from one state to another.
    - **Operations:** Actions a class can perform, captured as functions or methods within the class definition.
    - **Signals:** Asynchronous messages facilitating communication between objects during activity execution.
    - **Links:** Connections between objects illustrating their relationships.
- **Use-Case Diagrams:** These diagrams provide a high-level, user-centric view of system behaviour by depicting interactions between users (actors) and system functionalities (use cases).
    - **System:** The defined scope within which use cases and actors operate.
    - **Use Case:** Represents a specific system functionality accessible to users.
    - **Actor:** Represents a user or external system interacting with the system's use cases.
    - **Dependencies (Include and Extend):** Relationships between use cases, indicating shared or extended functionalities.
    
    **Interaction Diagrams:** Visualise the flow of messages between objects, offering a detailed perspective on object interactions.
    
    - **Sequence Diagrams:** Emphasise the chronological order of message exchanges between objects.
    - **Collaboration Diagrams:** Highlight the structural organization of objects and their communication links.
- **Activity Diagrams:** Illustrate the flow of activities within a system, depicting sequential, branching, and concurrent operations.
    - Employ various elements like action states, control flows, object flows, decision points, and swim-lanes to depict complex workflows.
- **CRUDE Analysis:** A technique to identify and define the fundamental operations (Create, Read, Update, Delete, Execute) that objects can perform within a system. This matrix-based approach helps analyse object interactions and responsibilities, particularly in the context of GUI entities.

## Behavioural Modelling Basics

The **behavior model** in object-oriented modelling (OOM) captures the internal workings of a system, illustrating how its components interact over time to fulfill specific functions. It complements the **structural model**, which depicts the static relationships between objects, by providing a dynamic perspective.

The objective of behavioural models is to display the fundamental objects in a problem domain that will work together to form a collaboration to support each of the use-case. At the same time, the structural model represents the objects and the relationships between them. 

The fundamental elements with behavioural modelling are ——

- Interactions & Object Diagrams
- Use Case Diagrams
- Interaction Diagrams
    - Sequence Diagrams
    - Collaboration Diagrams
- Activity Diagrams
- State Machine Diagrams

In essence, behavioural modelling tools within OOM equip you allows us to visualise and understand the dynamic interactions within a system. This understanding is paramount for designing robust, adaptable, and user-centric software solutions.

## Interactions & Object Diagrams

Communication between its various components lies at the heart of the every dynamic system. In OOM, objects interact by sending messages to each other in order to achieve specific goals. These interactions, composed of a series of messages, are crucial for understanding the system’s dynamic behaviour. 

**Object Diagrams**

Object diagrams visually represent a specific snapshot of objects and their relationships at a particular moment.

**Key Considerations for Constructing Object Diagrams:**

- **Objects** are the fundamental building blocks.
- **Links** connect the objects, representing their relationships.
- Objects should have **unique names** to identify them.
- Focus on the most important **elements relevant to the system** being modelled.
- Clearly explain the **associations between objects**.
- All **distinct** instances of objects and their specific attribute values should be represented.
- **Add comments** to the diagram for clarity and explanation where needed.

## Use Case & Use Case Diagrams: **A Dynamic View**

Use Case diagrams represents the dynamic behaviour of the system, are a key element of the Unified Modelling Language (UML). It provides a dynamic view of system behaviour by illustrating how users (actors) interact with a system to achieve specific goals (use cases). These diagrams offer a high-level understanding of system functionality without delving into implementation details.

It is represented in the form of an **ellipse. Use case** diagrams contains actors, use-cases and their relationships. A single use-case diagram is used to represent a particular functionality of the system. 

**Purpose and Objectives:**

- **Identifying System Requirements:** Use Case diagrams help to clarify and define system requirements by capturing the interactions between users and the system. This process ensures that the system is designed to meet user needs.
- **External Perspective:** They provide an external view of the system, showing how users perceive and interact with it. This external focus helps stakeholders and developers align on system functionality.
- **Influence of Internal and External Factors:** Use Case diagrams illustrate how internal system components and external entities (actors) influence the system's behaviour, ensuring a comprehensive understanding of system interactions.
- **Visualising Relationships and Events:** They visually represent the relationships between different use cases and actors, highlighting dependencies and the flow of events within the system. This visualisation aids in understanding system complexity and dependencies.

### **Key Elements of a Use Case Diagram:**

- **System:** Represented by a rectangle, the system boundary defines the scope of the system being modelled. Use cases are placed inside the boundary, while actors interact from outside.

- **Actor:** Actors, illustrated as stick figures outside the system boundary, represent users or external systems that interact with the system. Each actor has a specific role and initiates interactions to achieve particular goals.

### How to draw a Use Case Diagram?

1. Identify all the use cases
2. Identify all the actors
3. Generalise the relationship between use cases and actors.

Guidelines to be followed when drawing use-case diagram. 

- The diagram should be drawn from the user's perspective.
- The diagram should not include implementation details.
- The diagram should be easy to understand.
- Name should reflect the functionalities it performs.
- Relationship & Dependencies should be clearly defined.

### **Dependencies in Use Case Diagrams:**

Every model consist of many use cases. Dependencies information is used by the Use Case to execute system functionalities. 

- **Include Dependencies:** Indicate that a use case (base case) relies on another use case (Inclusion Use Case) to complete its functionality. This relationship is depicted with a dashed arrow from the base use case to the included use case, labeled with "<<include>>".
Include dependency behaviour is same as a Use Case. It is common to other Use Cases and added as Use Case that can be used in other use cases.
- **Extend Dependencies:** Represent optional behaviour that can extend the functionality of a base use case. The extended use case is dependent on the base case and is typically triggered by specific conditions. A dashed arrow, labeled "<<extend>>", points from the extended use case to the base use case.

### **Applications of Use Case Diagrams:**

- **Requirement Analysis:** Capturing and analysing system requirements from a user-centric perspective.
- **System Modelling:** Creating a high-level model of the system's functionalities and interactions.
    - **High-Level Design:** Guiding the design process by defining the scope and interactions of system components.
- **Forward and Reverse Engineering:** Aiding in understanding and documenting existing systems (reverse engineering) and guiding the development of new systems (forward engineering).
- **Communicating the System's Idea:** Presenting a clear and concise visualisation of the system's core functionalities to stakeholders.

## **Interaction Diagrams: Capturing Dynamic Behaviour**

Interaction diagrams, a core component of the Unified Modelling Language (UML), visualise the dynamic interactions between objects within a system. They illustrate how one or more systems connect & communicate with each other.  
Unlike static diagrams like class diagrams, which depict the structure of a system, interaction diagrams **emphasise the flow of messages between objects over time**. This dynamic perspective is essential for understanding **how a system behaves in response to events and how different parts of the system work together**.

**Key Elements of Interaction Diagrams:**

- **Objects:** Represented as rectangles with object names underlined, objects are the fundamental units of interaction.
- **Lifelines:** Vertical dashed lines that extend downward from an object, lifelines represent the object's existence over time.
- **Messages:** Represented as arrows between lifelines, messages depict the communication between objects. The arrow's direction shows the message flow, and message names often include parameters passed between objects.
- **Activations:** Represented as thin rectangles on lifelines, activations indicate the period during which an object is active, typically while processing a message.

Interaction diagrams include **Sequence & Collaboration Diagrams**

- **Sequence Diagrams:** Sequence diagrams emphasise the chronological order of message exchanges between objects. It flows from left to right. The **vertical axis represents time**, flowing from top to bottom, while the **horizontal axis represents the participating objects**, ***depicted as lifelines***. Messages, depicted as arrows, illustrate the communication between these objects, with the arrow's direction indicating the message flow. Sequence diagrams excel at illustrating the time-dependent behaviour of a system, making them suitable for analysing real-time or time-critical applications. It focuses on time sequence of messages.

![Untitled](Untitled%2045.png)

- **Collaboration Diagrams:** Collaboration diagrams, also known as communication diagrams, prioritise the structural organisation of objects and their relationships while illustrating message exchanges. 
These diagrams use object diagrams as their foundation, with numbered arrows representing the sequence of messages between objects. Unlike sequence diagrams, where time is explicitly represented, collaboration diagrams rely on message numbering to convey the order of interactions. Collaboration diagrams excel at visualising complex object relationships and message flows, making them suitable for analysing systems with intricate object collaborations.
    
    ![Untitled](Untitled%2046.png)
    

Two diagrams are used for the selection of the requirement. If the time sequence is preferred, then sequence diagram is used, and when the organisation is required, then a collaboration diagram is prefferred.

**Applications of Interaction Diagrams:**

- **Modelling System Behaviour:** Interaction diagrams capture the dynamic behavior of a system, illustrating how objects interact to achieve specific goals.
- **Visualising Message Flow:** They clearly show the sequence and flow of messages between objects, aiding in understanding system dynamics and object collaborations.
- **Validating System Design:** Interaction diagrams serve as a tool for validating system design by visualising how objects should interact to fulfill requirements. They can help identify potential design flaws or inconsistencies in object collaborations.
- **Documenting System Functionality:** These diagrams act as documentation for the dynamic aspects of a system, providing insights into how different parts of the system interact.

**Relationship with CRUDE Analysis**
While activity diagrams model the flow of activities, CRUDE analysis focuses on identifying the basic operations (Create, Read, Update, Delete, Execute) that objects within a system should support.  CRUDE analysis helps in designing object interactions and responsibilities, which can then be reflected in the activities depicted within an activity diagram.

## **CRUDE Analysis: Unveiling Object Interactions**:

CRUDE analysis stands for **Create, Read, Update, Delete, and Execute**. It's a method used to pinpoint the fundamental operations that objects within a system should be capable of performing. This analysis proves particularly valuable when used in conjunction with Use Case analysis, as it helps map out how objects interact and collaborate to fulfil the system's requirements.

**CRUDE Matrix: Visualising Object Responsibilities**:

A CRUDE matrix is a table that visually represents the interactions and permissions associated with objects in a system. The matrix is structured with:

- **Rows:** Representing the different classes or objects in the system.
- **Columns:** Representing the CRUDE operations (Create, Read, Update, Delete, Execute).

Each cell within the matrix indicates whether an object (represented by the row) has permission to perform a particular CRUDE operation (represented by the column) on another object. This representation provides a clear overview of object responsibilities and interactions.

**Benefits of CRUDE Analysis:**

- **Identifying Object Interactions:** CRUDE analysis helps systematically identify the necessary interactions between objects in a system.
- **GUI Entity Analysis:** It aids in understanding how GUI entities are used and how they relate to the underlying objects and operations.
- **Ensuring Class Instantiation:** By analyzing the CRUDE matrix, you can verify if every class in the system can be instantiated, ensuring completeness in the object model.

**Example:**

The sources provide an example of a CRUDE matrix for a publishing service model. The matrix outlines the permissions for roles like Manager, Writer, Editor, and Publish, indicating which roles can Create, Read, Update, Delete, or Execute specific entities within the system.
