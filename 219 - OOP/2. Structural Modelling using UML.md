## Overview

This chapter  focuses on **structural modelling** with UML, particularly on **class diagrams** which provide a static view of a system's structure.

**UML:** A standardised modelling language for software systems, distinct from programming languages.

**Benefits** 

Clearly specifies system structure and behaviour, simplifies complex systems, aids team communication, and is platform-independent.

**Structural Modelling ———** Represents a system's static structure through:

1. **Classes**
Templates for objects, grouping those with common attributes, operations, relationships, and semantics.
    - Identified by analysing nouns in system descriptions and use cases.
    - Abstractions, focusing on essential properties.
2. **Relationships**
Connections between classes.
    - **Dependency:** One class relies on another.
    - **Generalisation:** "Is-a" relationship, where a subclass inherits from a superclass.
    - **Association:** "Has-a" relationship, connecting objects for data communication.
        - **Aggregation:** A specialised association, "whole-part" relationship.
3. **Common Mechanisms:** Notations enhancing diagram clarity:**6**
    - **Notes:** Comments or explanations.
    - **Stereotypes:** Custom model elements.
    - **Constraints:** Restrictions on model elements.
    - **Tagged Values:** Additional element properties.

**Class Diagrams:** Graphs visually representing classes, interfaces, and their relationships.

**Advanced Structural Modelling:** Builds upon basic elements with:

- **Interfaces:** Define behaviour without implementation.
- **Types:** Stereotyped classes without methods, often conceptual.
- **Roles:** Specific behaviours of objects within a context.

**Other Important Diagrams:**

- **Object Diagrams:** Represent instances of classes and their relationships at a specific point in time.
- **Package Diagrams:** Group related model elements to manage complexity.

This chapter explains how to create these diagrams and highlights their importance in system documentation and communication among development teams. It emphasises the advantages of UML in representing complex systems and facilitating efficient software development.

## UML (Unified Modelling Language)

Modelling is tested and well-known technique that helps build a model. Model is a blueprint of the real system that needs to be built.

The Unified Modelling Language (UML) is a standardised modelling language used to build models for software systems. It's important to understand that UML is distinct from programming languages like C++ or Java. Think of UML as a visual blueprint for software.

### **Types of UML Diagrams**

UML diagrams are categorised into two main views:

1. **Static (or Structural) View**
    
    Focuses on the system's static structure using objects, attributes, operations, and relationships. 
    
    Structural diagrams do not employ time-connected concepts and do not display the details of dynamic behaviour. This view includes diagrams like:
    
    - **Class diagrams**
    - **Object diagrams**
    - **Component diagrams**
    - **Deployment diagrams**

1. **Dynamic (or Behavioural) View**
    
    Represents the system's dynamic behaviour and how it changes over time. Examples of dynamic view diagrams are:
    
    - **Use case diagrams**
    - **Interaction diagrams (including sequence and communication diagrams)**
    - **Activity diagrams**
    - **State machine diagrams**

1. **Architectural Modelling**
    
    The architectural modelling represents the complete framework of the system i.e, it contains both structural and behavioural elements of the system.
    
    Architectural model can be expressed as the entire blueprint of the system.

### **Key Benefits of UML**

1. **Clear Communication**
    
    UML provides a standardised way to specify a system's structure and behaviour. This makes it easier for development teams to communicate and understand complex systems.
    
2. **Simplicity**
    
     It helps to break down large, complex systems into smaller, more manageable parts.
    
3. **Team Onboarding**
    
    New team members can quickly grasp the system design using UML diagrams.
    
4. **Platform Independence**
    
    UML models are not tied to a specific operating system or programming language. This means that developers working on different platforms can still understand and use the same UML models.

UML plays a crucial role in various stages of software development, including:

- **Requirements Analysis**
- **System Design**

Structural modelling describes the static features of a system and uses classes to collect the system's vocabulary. Structural modelling provides a structural view of a system. It highlights the structure of objects, which includes their classifiers, relationships, attributes, and operations.

These elements make up the vocabulary of the system being modelled. To create a structural model, you must first gather key data from the problem domain. The **class diagram is one of the most important structural models in UML**. The core elements of structural modelling are. —— **Class, Interface, Component, Node, Constraints**

### **Classes**

Classes are an essential structure of any object-oriented system. They describe a group of objects that share common attributes, operations, relationships, and semantics.

When developing a system, **classes help collect the system's vocabulary**. These classes can be used to represent hardware, software, or conceptual things. Classes ***describe only the attributes that are important to an application and ignore the rest.*** This is known as **abstraction**, an important feature of object-oriented concepts.

- **Points for Creating a Class**
    - **Unique name**: Each class must have a unique name that is a textual string comprised of any number of letters, numbers, and punctuation marks.
    - **Optional Attributes**: A class may or may not have attributes, which are defined by a name that contains a series of values. For example, the "Person" class has attributes like name, age, and address. You can include the attribute's type, such as string or integer, in the class diagram.
    - **Optional Operations**: A class may or may not have operations, which describe the behaviour of the class. Operation names, which are usually written as a short text string, represent some behaviour of the class. For example, the "Car" class may have operations like "move" and "repair". You can identify an operation by declaring its signature.
    - **Visibility**: You can define the visibility of class members, such as attributes and operations, using the following:
        
        **(+)** for public: visible to all elements
        
        **(-)** for private: visible only to the classifier itself
        
        **(#)** for protected: visible only to the descendants and the classifier itself
        
        **(~)** for package: visible to all classifiers within the same package.
        
    

### Relationships

Relationships in UML define how classes communicate with each other. The three basic relationship types in UML are dependencies, generalisations, and associations.

- **Dependencies** describe relationships where changes to one class can impact another class. For instance, if a class named "Vehicle" utilises the properties and operations of another class called "Bodyshop," this constitutes a dependency. 
It's important to note that this dependency might not work in reverse, meaning changes to "Vehicle" might not necessarily affect "Bodyshop."
- **Generalisation** is a “a-kind-of” relationship that creates relationships between a superclass (base class) and a subclass, enabling inheritance of attributes and operations.
For example, we can say that a "Car" is a kind of "Vehicle."**2** In this context, "Vehicle" would be the superclass, and "Car," inheriting properties from "Vehicle," would be the subclass.
- **Association** is a “a-part-of” relationship between classes. It connects classes where objects from one class are linked to objects from another class for data communication. An example of association is the relationship between "Schools" and "University," where "Schools" work for the "University.”
    
    **Aggregation** is a specific **type of association** that represents a "whole-part" relationship. This relationship is illustrated by an aggregate (the whole) and its constituent parts. For example, a "University" having numerous "Schools" exemplifies aggregation, as "Schools" are considered parts of the "University.

### Common Mechanisms

Common mechanisms, such as notes, tagged values, stereotypes, and constraints, can be used to further describe information in UML diagrams.

- **Notes** are used to provide comments and explanations for documentation purposes. These are tagged value as a string enclosed in {brackets}.
- **Tagged values** create extensions, or new information, about the properties of a UML element.
- **Stereotypes** create new building blocks that allow for the use of basic elements with special properties. These are text name inside guillemets(<< >>) and place them above the name of another element.
The three stereotypes such as **call, copy** and **become** are used when modeling interactions among objects. And, some stereotypes such as **instanceOf**, **instantiate, bind** and **friend** are used to dependency relationships among classes and objects in class diagrams.
- **Constraints** are conditions placed on UML elements that are checked at run-time. These are string enclosed in {brackets} and can be put in a note.

When you use these notations in your UML diagram, keep in mind such points as always use short notes, use notes only when the facts cannot be conversed using UML, do not use too many graphical stereotypes, tagged values and constraints; use only common and simple supplements.

## Advanced Structural Modelling

**Advanced Structural Modeling** in UML builds upon basic structural modeling by incorporating more intricate details and features. It encompasses refining classes and relationships to enhance the precision and expressiveness of the structural model.

## Classifiers in UML

A **classifier** in UML is a fundamental building block that defines the structural and behavioural characteristics of elements within a system. It serves as a blueprint for creating instances, which are concrete representations of the classifier. Classifiers encompass a range of elements, including:

- **Classes:** A class represents a blueprint for creating objects that share common attributes, operations, relationships, and semantics. They encapsulate data (attributes) and behavior (operations).
- **Interfaces:** An Interface defines a contract or a set of operations that a class or component must adhere to. It specifies the expected behavior without providing any implementation details.
- **Datatypes:** Datatypes represent data values that do not possess identity. Examples include primitive types (e.g., Integer, String) and enumeration types (e.g., Boolean).
- **Nodes:** A node depicts a physical or virtual element that represents a computational resource at runtime, such as a server, workstation, or sensor.
- **Signals:** Signals denote asynchronous communication events exchanged between objects. They represent stimuli that can trigger state transitions within an object's lifecycle.
- **Use Cases:** A use case captures a sequence of actions performed by an actor (user or external system) interacting with the system to achieve a specific goal. It describes system functionality from an external perspective.
- **Components:** Components represent modular parts of a system that encapsulate functionality and can be independently deployed and replaced. They typically group related classes or other components to provide a higher level of abstraction

## Advanced Classes

In advanced modeling, classes can be further specified using attributes such as visibility, scope, multiplicity.

**Visibility** 

It defines the accessibility of a classifier's attributes and operations by other classifiers. The symbols used to denote visibility are:

- **+** Public: Accessible to all elements.
- - Private: Accessible only within the classifier itself.
- **#** Protected: Accessible only by descendants of the classifier and the classifier itself.
- ~ Package: Accessible to all classifiers within the same package.

**Scope** 

It specifies if an attribute or operation is unique to each instance of the class or shared among all instances. There are two scope specifiers:

- **Instance Scope:** A unique attribute or operation exists for each instance of the class.
- **Class Scope:** A single, shared attribute or operation exists for all instances of the class.

![Untitled](Untitled%2021.png)

**Multiplicity** 

It indicates the number of instances of one class that can be associated with a single instance of another class. For instance, a "one-to-many" multiplicity between "University" and "Schools" would mean one university can have multiple associated schools.

You can display a multiplicity of exactly one (1), zero or one (0..1), many (0..*), or one or more (1..*)

## Advanced Relations

UML provides various advanced relationship properties for detailed modeling, including:

- **Navigation:** Specifies the direction of the relationship between classes. It clarifies if the relationship can be traversed from one class to another and vice versa.
- **Qualification:** A qualified association utilises a qualifier, which is a special attribute, to narrow down the multiplicity of an association at its target end. For instance, in a "Bank" and "Customer" association, the account number could serve as a qualifier, limiting the multiplicity from "many" to "one" as each unique account number is linked to only one customer.

## Interfaces, Types and Roles

**Interfaces:** Interfaces in UML specify a collection of operations that a class or component must implement. They define a contract without providing any implementation details. Interfaces can participate in relationships like dependency, generalisation, association, and realisation.

**Types:** A type represents a stereotype of a class that is primarily used during the analysis phase. It helps conceptualise potential classes without defining methods or instances.

**Roles:** A role describes an object's specific behavior within a particular context. For instance, an "Employee" class might have different roles such as "Manager," "Cashier," or "Teller" within a "Bank" system.

## Package Diagram

Package is a namespace used to combine logically related elements within a system and each element should be a package-able element that consists of components, use cases, and packages themselves.

Package diagrams in UML illustrate the organization and dependencies of packages, which are mechanisms for grouping related elements within a model. These diagrams are crucial for representing the high-level structure of complex systems and are particularly valuable for ——

- **Organising Large Models:** They help manage complexity by decomposing systems into manageable modules.
- **Illustrating Subsystem Structure:** Package diagrams clarify the relationships between different subsystems or modules within a system.
- **Depicting Dependencies:** They visually represent the dependencies between packages, such as usage relationships or import dependencies, aiding in understanding the impact of changes.

![Untitled](Untitled%2028.png)

Sometimes your package is accessed by another package, or a package that is dependent on your package is called a **dependent package**. 

A plus sign (+) within a circle is drawn at the end attached to the package indicating that the package has branches or sub-packages.

**Key Elements of a Package Diagram**

- **Packages:** Represented visually as folders, packages group related elements, including classes, interfaces, other packages, use cases, and diagrams. Each element is uniquely owned by a single package. A "+" symbol within a circle next to the package name signifies that the package has sub-packages.
- **Dependencies:** These relationships between packages denote that changes in one package might affect others. Two primary dependency types are used in package diagrams:
    - **Import Dependency:** Indicates that one package imports and utilises functionality from another.
    - **Access Dependency:** Signifies that one package requires access to elements or services offered by another package
- **Merge:** A directed relationship where the contents of one package are extended by another, combining their contents to create a new package, as exemplified by the "Cart" package.

**Package Visibility**

Packages have two visibility levels:

- **Public (+):** Elements within the package are accessible from outside the package.
- **Private (-):** Elements within the package are only accessible from within the package.

![Untitled](Untitled%2029.png)

Figure 2.16 depicts a package diagram for a system with "Web Store" and "Book Store" packages. These packages merge into a "Cart" package and rely on a "Payment" package. Additionally, the "Payment" and "Cart" packages import functionalities from "Customer" and "Inventory" packages.

**Package Naming**

Packages are identified by unique names. These names can be:

- **Simple Names:** A straightforward text string representing the package name.
- **Qualified Names:** A hierarchical name separated by double colons (::), reflecting the package's position within a hierarchy.

## Instance & Object Diagrams

**Object diagrams** and **instance diagrams** are closely related UML diagrams used to visualise and exemplify objects and their interconnections in a specific scenario or state of a system. 

They are valuable for understanding how objects collaborate and exchange data at a given point in time. Both diagrams share similar notation and are often used interchangeably.

**Instance Diagrams**

An **instance diagram** focuses on illustrating the relationships between a specific set of objects and their values at a particular moment. They are particularly useful for:

- **Clarifying Complex Class Diagrams:** Providing concrete examples of how objects from different classes are linked.
- **Documenting Test Cases:** Visualising the state of objects and their relationships during specific test scenarios.

**Key Differences and Applications**

While the terms "instance diagram" and "object diagram" are often used interchangeably, the subtle distinction lies in their focus:

- **Instance diagrams** emphasise illustrating specific instances and their interrelationships in a particular scenario.
- **Object diagrams** provide a more general snapshot of object interactions at a given time.

Both diagrams are valuable for:

- **Understanding Object Collaboration:** Visualising how objects interact and exchange data in a specific context.
- **Communicating System State:** Depicting the state of objects and their relationships at a particular moment in time.
