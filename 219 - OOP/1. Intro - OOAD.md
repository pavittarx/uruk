## Object Orientation

Object orientation is a **software development approach** that **emphasises the organization of software** as a **collection of discrete, reusable objects that interact to achieve a specific functionality**. It's a way of thinking about problems and designing solutions that closely mirrors how we perceive the real world.

The shift towards object orientation was fuelled by the limitations of traditional, structured programming methods in managing increasingly complex software systems. These limitations, collectively referred to as the "Software Crisis," led to software that was difficult to maintain, modify, and extend. 

Object orientation addresses these challenges in several ways:

- **Improved Code Reusability:** Object-oriented programming languages promote the creation of reusable components (objects), reducing development time and effort.
- **Enhanced Maintainability:** By encapsulating data and operations within objects, object orientation makes it easier to modify and maintain software without impacting other parts of the system.
- **Increased Flexibility and Extensibility:** The use of inheritance and polymorphism makes object-oriented software more adaptable to changing requirements and easier to extend with new functionalities.
- **Closer Alignment with Real-World Concepts:** Object-oriented modeling represents systems as interacting objects, making the design process more intuitive and aligned with how we perceive the world around us.
- **Support for Complex Systems:** Object orientation provides a structured framework for managing complexity by breaking down large systems into smaller, manageable objects and their interactions.

Object orientation has become a dominant paradigm in software development, underpinning popular programming languages and influencing software design principles across various domains

## OOAD Approach

The OOAD approach is a sequential process for developing software systems using object-oriented principles. This approach is widely used in object-oriented software engineering.

The first phase, analysis, focuses on establishing system requirements and performing domain analysis from the customer's viewpoint. This phase involves understanding the problem by examining real-world concepts using various models.

Once the analysis phase is complete, the design phase begins, which is iterative. The design phase maps the logical design to the physical design. In this phase, the **object** is a key construct, representing an instance of a class and containing data structure along with behavioral characteristics. Following the design phase, a prototype is created and tested.

## OOM (Object Oriented Modelling)

**OOM is a key aspect of OOAD**, involving the visualization of systems using models based on real-world concepts. It is a helpful technique for managing complex systems. 

The primary goal of OOM is to identify and organize application objects within their domain without focusing on implementation in a specific programming language. 

This approach encourages developers to consider the application domain throughout the software engineering lifecycle, requiring them to identify and organise the application's inherent processes, comprehend the system, and then elaborate on its data structure and functions.

Once the system model is complete, it can be implemented in any suitable programming language. Developers must analyze bad designs to understand how to create good ones. Therefore, OOM analysis is crucial for proper system design.

The implementation in a programming language occurs only after the system modeling is complete.

**Steps of the OOM Process**

The OOM process involves four main steps:

- **Requirement Analysis of System:** This step involves formulating a problem statement and building a system model that reflects real-world scenarios. The objective is to create a model comprehensible to application experts, regardless of their programming expertise. All system requirements and properties should be defined in this phase.
- **System Design:** In this step, the complete system architecture is designed, dividing it into subsystems based on the system analysis model and the proposed architecture.
- **Object Design:** This step involves developing a design model based on the analysis model from the previous phase. It defines the data structures and algorithms for implementing each class, using the analysis model's implementation details.
- **Model Implementation:** The final step involves implementing the classes and relationships developed during object design using a specific programming language. This includes implementing the database and hardware, if necessary.

## Object-Oriented Modelling Technique (OMT)

The OMT, developed as a productive and practical approach for object-oriented analysis and design, covers various aspects of software development. OMT uses three types of models for a comprehensive system description:

- **Object model**
Describes the objects in the system and their relationships. **Object models** are represented graphically through **class diagrams** and **object diagrams.**
- **Dynamic model**
The dynamic model depicts the interactions between objects and how information flows within the system.
Dynamic models focus on **three key elements: time, states, and transitions between states.** These models also incorporate **events that trigger transitions** and the **actions that result from these events.**
- **Functional model:** Describes data transformations within the system. **Functional models** are represented using Data Flow Diagrams (DFDs). Key elements of DFDs include entities, data stores, processes (or operations), file stores, and data flow.

All three models are relevant throughout the development stages and contribute to capturing the system's implementation details. A system description is incomplete without adequately describing all three models.

## Object Oriented v/s Structured Approach

Object-oriented development differs from the structured approach, which priorities specifying and decomposing system functionality. 

One drawback of the structured approach is that changes in system requirements often necessitate significant restructuring, making the system harder to manage over time. 

In contrast, the object-oriented approach emphasises identifying objects from the application domain and then designing procedures (methods) around them. Instead of focusing on individual functional requirements, it takes a holistic view of the application domain, identifying objects within the problem domain. 

This holistic approach provides an advantage for object-oriented development, facilitating system enhancement and reducing the need for major code modifications when adding new features.

## Principles of Object Orientation

There are four key principles of object orientation. These principles are **abstraction**, **encapsulation**, **inheritance**, and **polymorphism.**

**Abstraction** is a core concept in object-oriented systems that involves representing the essential aspects of an object while omitting any incidental properties. This principle emphasises focusing on what an object does rather than how it is implemented. A real-world example of abstraction is using a mobile phone to make a call. The user only needs to open the phone app and press a button, but many behind-the-scenes processes occur that are hidden from the user.

**Encapsulation**, also known as **information hiding**, is the practice of shielding certain data within an object from outside access while exposing other data. This principle focuses on separating the internal workings of an object from its external interface. Encapsulation helps improve system flexibility and maintainability by allowing developers to change the internal implementation of an object without affecting its external behavior.

**Inheritance** promotes code reusability in object-oriented development by allowing developers to create new classes (subclasses) based on existing classes (superclasses). Subclasses inherit the attributes and operations of their superclasses. For example, a "Savings Account" class could inherit properties from a more general "Account" class. **Generalisation** and **specialisation** are closely related to inheritance. Generalisation describes the relationship between classes in a hierarchy. Specialisation refers to the process of creating more specific subclasses from a general superclass.

There are two types of inheritance: single inheritance and multiple inheritance. **Single inheritance** occurs when a subclass inherits from only one superclass, as shown in the relationship between the classes "Circle," "Triangle," "Square," and "Shape," where the first three classes inherit from the "Shape" class. **Multiple Inheritance** occurs when a subclass inherits from more than one superclass.

**Polymorphism**, which means "many forms," is closely tied to inheritance and enables objects of different classes to be treated as if they were objects of a common superclass. For example, a program designed to calculate the area of different shapes could use a single "Find_Area" operation that adapts based on the specific shape being analysed. Polymorphism enhances flexibility and simplifies maintenance by allowing new classes to be added without requiring modifications to existing code

**class and objects**, **links and association**, and **generalisation and inheritance**.

### Class and Objects

A **class** acts as a template for creating **objects**. An object is an instance of a class, similar to how a specific car, like a Honda Civic, is an instance of the class "car."

Classes group similar objects based on their shared characteristics, referred to as **attributes**, and behaviors, referred to as **operations. Attributes** are **data values** associated with a class, while **operations** represent **actions** that objects within that class can perform. For example, if "car" is a class, attributes might include "color," "make," and "model," while operations could include "start," "stop," and "accelerate.”

### Links and Association

**Links and associations** represent the relationships between classes and objects within an object-oriented system. A **link** represents a specific connection between two or more objects, such as a student named John being enrolled in a specific course.

An **association** represents a broader relationship between classes, such as students being enrolled in courses, without specifying individual instances. For instance, an association might state that "students can enroll in multiple courses," while a link would specify that "John is enrolled in CS 101.”

**Aggregation**, a specific type of association, represents a "whole-part" or "has-a" relationship between classes. This concept helps model systems where one class (the whole) consists of multiple instances of another class (the part). For example, an "Exam Schedule" (the whole) might consist of multiple "Exam" objects (the parts).

A key characteristic of aggregation is **transitivity**. If class X is part of class Y, and class Y is part of class Z, then class X is also considered part of class Z. However, it's essential to clarify that this **transitivity in aggregation does not necessarily imply that the lifetime of the part object is tied to the lifetime of the whole object.**

### Generalisation and Inheritance

**Generalization and inheritance** are closely related concepts that promote code reuse and represent hierarchical relationships between classes. **Generalisation** describes an "is-a-kind-of" relationship between a superclass (parent class) and a subclass (child class). 
For example, a "Savings Account" is a kind of "Account." This relationship allows the subclass to inherit the characteristics and behaviours (attributes and operations) of its superclass, reducing redundancy and promoting code organization. **Inheritance** is the mechanism that allows subclasses to inherit characteristics and behaviours from their superclasses. For example, a "Savings Account" class would inherit the "balance" attribute and the "deposit" and "withdraw" operations from the "Account" class.

## Identifying Classes in Object-Oriented Modeling

Identifying classes is a crucial step in object-oriented modeling, as it lays the foundation for representing the system's structure and behavior. This process involves understanding the system and establishing relationships between the identified classes. 

**Textual analysis,** a technique commonly employed for class identification, involves examining the problem statement and related documents to extract relevant nouns and verbs. 

### 3 Step Process to Identify Classes

1. **Identify Nouns**
    - Carefully analyze the problem statement and associated documentation.
    - Highlight all the nouns present in the text.
    - Engage in discussions with clients or domain experts to gather additional insights and identify potential nouns related to the system
2. **Evaluating Nouns for Class Identification**
    - **Relevance and Scope:** Determine if the identified noun is genuinely needed within the project's scope
    - **Problem Domain Resource:** Assess if the noun represents a resource or concept within the problem domain. If yes, devise an appropriate class name that reflects the resource it represents
    - **Class Instance (Object):** Analyse if the noun is an instance or example of a class rather than a class itself.
    - **Class Attribute:** Determine if the noun represents a property or characteristic of a class
    - **Attribute Value:** Analyse if the noun is a specific value of an attribute belonging to a class
3. **Defining the Purpose**
    - Provide a clear and concise description explaining why the identified class is an essential resource within the problem domain

## QnA’s

- **What is Object Orientation?**
    
    Object orientation is a method for software development that utilises objects, which have both **state (what they know)** and **behavior (what they can do)**.
    
    Object-oriented analysis and design (OOAD) is an approach for developing software systems that uses the concepts of object-oriented software engineering. 
    
    This widely-used approach to software engineering consists of analysis and design phases. In the analysis phase, system requirements are established and the problem domain is analysed. This is followed by the design phase, an iterative process in which the logical design of the system is mapped to the physical design.
    
    **Object-oriented modeling (OOM)**, which is not tied to a particular programming language, visualizes systems using real-world concepts. It can be used to understand problems, model enterprises, design programs, and design databases. 
    
    Some important elements of OOM include the following:
    
    - **Analysis:** Analysis ensures a system works in a real-world context.
    - **Objects:** Objects have both state (what they know) and behavior (what they do).
    - **Classes:** A class is a blueprint for creating objects
        
        
    
    The **object modeling technique (OMT)**, which is a practical method for developing software, encompasses aspects of object-oriented analysis and design. Unified Modelling Language (UML), a standard modelling language, is a tool used in OOM and OOAD.
    
- **What is the basic philosophy of Object Orientation?**
    
    A fundamental characteristic of object-oriented systems is the **sharing of structure and behavior**, which is primarily achieved through **inheritance**. 
    Inheritance allows for the reuse of code, as common structures (base classes) can be utilised in creating subclasses. This promotes reusability and extensibility, as new characteristics can be added to a system by extending existing features through inheritance. However, simply employing object orientation doesn't automatically guarantee reusability and enhancement, which requires a more generalised system design.
    
    Another important aspect of object orientation is the **prioritisation of object structure over operation implementation**. This means that specifying the characteristics of objects within a system takes precedence over implementing those characteristics. 
    
    Object-oriented development emphasises identifying objects from the application domain and then defining procedures or methods around these objects. This contrasts with the structured approach, which emphasises specifying and decomposing system functionality. Changes in system requirements often necessitate significant restructuring in systems built using the structured approach, while systems based on object structure are more adaptable.
    
    The emphasis on object structure stems from the observation that the ways in which an object is used can change frequently during development, while the features an object provides are more stable. By focusing on the essential properties of objects and their roles within a system, developers can create more robust and maintainable software.
