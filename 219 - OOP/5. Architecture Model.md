## Overview
- A model is an abstract representation of a system that simplifies understanding and communication among project team members. 
- Models capture essential aspects while omitting unnecessary details and can be expressed using modeling languages like UML. 
- Models offer a blueprint for system visualization, complexity reduction, and communication with end-users.

Architectural modeling, provides a comprehensive view of a software system's structure and behavior. Architectural modeling encompasses both structural and behavioral diagrams, offering logical and physical perspectives.
- **Logical Architecture** focuses on the system's design structure and organization from the end user's functional requirements perspective. It provides a top-down abstraction of the overall system design and a static view of its objects and classes.  UML diagrams used to represent logical architecture include class, object, sequence, activity, and state diagrams.
- **Physical Architecture**, on the other hand, represents the system's dynamic (runtime) architecture, showing the configuration of software components on the physical layer and their connections. It focuses on details like network resources, server configuration, and hardware information. The deployment diagram in UML is used to represent physical architecture, illustrating the mapping of software elements to physical platforms.

**Implementation Diagrams** play a crucial role in the physical realization of the design.
- **Component diagrams** model the system's physical aspects, including software components, source code, runtime code, and executables. They illustrate the arrangement and dependencies of components within a system.
- **Deployment diagrams** show the physical distribution of components on hardware nodes, depicting the runtime processing nodes and the components residing on them. They help visualize the system's physical structure, component deployment, and scalability.

**Collaboration**, represents the interaction of elements (classes, objects, interfaces, etc.) to fulfill system requirements. 
- Collaboration encompasses both structural and behavioral dimensions, addressing how elements work together and their runtime interactions. 
- Collaboration diagrams visualize these interactions, highlighting the roles of classifiers and their relationships in achieving system functionality.

## Model
A model is an abstract depiction of a system that aids in understanding and communicating its representation. It provides insights into the development process for project team members and offers a comprehensive view of system planning, design, testing, and implementation.

Models are essential because they simplify complex systems by capturing important aspects while omitting unnecessary details. They act as blueprints, facilitating visualization, analysis, and communication of the system's structure and behavior.

The creation and refinement of models is referred to as **modeling**. This process is crucial in software development because it clarifies the system's architecture, aiding in risk management and exploration of the desired structure and behavior.

Modeling encompasses two main classifications: static and dynamic models.
- **Static models** provide a structural perspective, detailing the system's components and their relationships without considering time-dependent aspects.
- **Dynamic models**, on the other hand, represent the system's behavior over time, illustrating how it interacts and changes in response to events or stimuli.

- Effective modeling necessitates a suitable medium for expression, with modeling languages like UML serving this purpose in software design.  
- Models can incorporate both visual representations (notations) and textual descriptions (semantic information) to enhance understanding and clarity. 
- The selection of an appropriate model is crucial, as different models serve different purposes and cater to varying levels of abstraction and stakeholder requirements.

## Architectural Modelling
Architectural modelling means to represent the high-level structure of software. It emphasizes the significance of architectural components and their interrelationships in fulfilling both functional and non-functional system requirements.

Architectural modelling employs multiple views or perspectives to provide a comprehensive understanding of a software architecture. These perspectives often include:
- **Logical Architecture (Logical View):** 
	- This view focuses on the system's design structure and organization from the user's perspective, abstracting the system's overall design based on functional requirements. 
	- It helps in understanding the structure and organization of system's design.
	- It starts with end user's functional requirements and provides a top-down abstraction of the system's overall design.
	- It illustrates the static relationships between software classes and their organization into packages, subsystems, and layers.
	- UML diagrams used to represent logical architecture for the object oriented systems include class diagrams, object diagrams, sequence diagrams, activity and state diagrams. 
	- This architecture only focuses on the main components, their association and data flow between them while structuring and grouping the elements into larger-scale modules. 

- **Physical Architecture (Physical View):** 
	- This view illustrates the system's dynamic (runtime) architecture, showing the arrangement and connections of software components on the physical layer, including hardware elements (nodes), network topology, and supporting software platforms.
	- This model focuses on detail about network resources, server configuration, hardware information and other relevant information required to develop and deploy the system. 
	- Its main objective is to satisfy the proposed logical architecture elements and defined requirements of the system. 
	- UML Deployment diagram is used to represent it. 
	- The physical architecture helps the system designers and administrators recognize the software's physical location, linkage between nodes, deployment and scalability.

### Different Aspects of Architectural Modelling
1. Static v/s Dynamic Aspect
	**Static aspects** encompass the system's stable components that constitute its primary
	structure, and do not change when the system is run or executed. 
	- This includes elements like **classes, interfaces, objects, components, and nodes,** which remain relatively unchanged during system execution.
	- It includes static diagrams like Class Diagram, Component Diagram, Deployment Diagram.
	
	**Dynamic aspects** focus on the system's behavior during runtime, including aspects like
	component communication, resource allocation, and changes in system configuration.
	- It includes diagrams such as use case, Sequence, Activity and State Chart Diagrams.

2. Functional v/s Non-Functional Aspect
	**Functional aspects** define how system functions collaborate to achieve overall goals and
	satisfy requirements. They drive the definition of views related to information flow,
	concurrency, deployment, and operational aspects.
	- It explores how software components interact among them and with the outer components of the system.

	**Non-functional aspects** address operational capabilities and constraints that influence the
	system's functionality, such as performance, security, reliability, and maintainability. These
	qualitative and subjective aspects are crucial for achieving desired quality of service.
	- The non functional aspect is a difficult task to accomplish.
	- The software architect applies architectural strategies (design patterns, layering techniques, etc.) to the system design in order to satisfy non functional aspects.  

Architectural modeling aids in managing software complexity by promoting abstraction, separation of concerns, and component reuse.  Architectural models act as blueprints for system development and guide design decisions, ultimately contributing to the creation of robust and well-structured software systems.

## Implementation Diagrams
- Use Case Diagram is closely correlated with the implementation diagram. 
- The reason for this coupling is to highlights which design elements will implement the functionality of the Use Case.
- The implementation view of the system incorporates the components that are used in the physical system. 
- The most used implementation diagrams are Component Diagrams, & Deployment Diagrams.

### Component Diagrams
Component diagrams illustrate the organization and relationships of physical components within a system.  
- The relationship among components are called dependencies.
- It represents the high-level parts that make up the system. These help us frame large systems using smaller components, and become necessary when building complex systems. 
- The component diagram also represent collaborations and internal structure of components.
- **Key elements** of a component diagram include:
	- **Components:** Represented as rectangles with a tab, components symbolize reusable software units. Each component encapsulates specific functionality and interacts with others through well-defined interfaces.

### Deployment Diagrams
Deployment diagrams visualize the physical deployment of software components onto hardware nodes. These diagrams are crucial for:
- **Understanding Physical Architecture:** They illustrate the hardware and software infrastructure upon which the system will run.
- **Planning Deployment:** They help in strategizing and visualizing how software components will be distributed and installed.
- **Managing Complex Deployments:** They are particularly helpful for embedded systems, client/server systems, and distributed systems.

**Key elements** of a deployment diagram include:

- **Artifacts:** Represented as rectangles with the artifact type specified, artifacts are the physical manifestations of software components, such as executable files, libraries, or configuration files.
- **Nodes:** Symbolized as cubes, nodes denote physical or virtual resources like computers, servers, or mobile devices. Each node represents a computational resource where artifacts are deployed.
- **Connections:** Represented as lines between nodes, connections depict the communication paths between physical resources. These lines might include labels to specify communication protocols or other relevant information.

In essence, implementation diagrams bridge the gap between the logical design of a system and its physical realization, offering valuable insights into how software components interact and are deployed within a specific hardware environment.

## Collaboration

The section "Collaboration" in Unit 5 of the source "MCS 219 B1.pdf" explains the concept of collaboration in UML and how it's represented using collaboration diagrams.  Collaboration in this context refers to the interaction between different elements of a system, showing how they work together to fulfill the system's behavioral requirements.  While a collaboration can be depicted using various elements like classes, objects, interfaces, and components, its essence lies in illustrating the dynamic interplay of these elements rather than merely their individual functionalities.

Collaboration encompasses both structural and behavioral dimensions. The structural dimension focuses on the arrangement and relationships between collaborating elements, while the behavioral dimension emphasizes the runtime interactions and message flow between these elements. Essentially, it provides a holistic view of how different parts of a system work together dynamically to achieve a common goal.

Collaboration diagrams are employed to visually represent collaborations in UML. They offer a structured way to depict:

- **Roles:** Within a collaboration, each participating element plays a specific role. Collaboration diagrams use a dashed ellipse to represent the collaboration itself, and boxes within the ellipse denote the roles of different classifiers. For instance, in a banking system collaboration, there might be roles like "Customer," "Account," and "Transaction."
- **Interactions:** The core of a collaboration lies in how different roles interact. Collaboration diagrams employ numbered arrows to illustrate the sequence of messages exchanged between roles. Each numbered arrow signifies a specific message flow, clarifying the communication pattern within the collaboration.

Key aspects of collaborations highlighted in the source include:

- **Focus on Behavior:** Collaborations emphasize the behavioral aspects of a system, illustrating how elements dynamically interact at runtime to achieve a particular functionality.
- **Abstraction:** They allow for a higher-level representation of system behavior without delving into the internal details of individual elements. This supports a more abstract and understandable model of complex interactions.
- **Templates for Runtime:** Collaborations serve as templates for runtime interactions. They define the roles and potential message flows, and at runtime, specific instances of classifiers are bound to these roles, enacting the defined interactions.

The source emphasizes the benefits of using collaboration diagrams, stating that they provide a simple and clear visual representation of complex systems, even when numerous elements and interactions are involved.  The source also notes that collaboration diagrams effectively communicate the system's design to both technical and non-technical stakeholders.
