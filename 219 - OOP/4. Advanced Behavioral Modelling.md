Advanced Behavioral Modelling using UML

## Overview

The behavioral modeling of a system in the **Unified Modeling Language (UML)** can be understood through the lens of **events, time, and signals**. UML employs these fundamental features to define a wide range of behaviors, including state machines and time-space diagrams, represented by arcs (transactions) and vertices (states).

Events in UML can be categorized as either internal or external. Internal events, also known as system events, occur within the system's boundaries, while external events originate outside the system. Events in UML are often modeled as operations within the object class. Signals, which are asynchronous messages transmitted between objects, are represented in a dedicated row within the class representation.

State machines are crucial in representing the behavior of objects within a system. An object's state, influenced by the events it receives, can transition from one state to another through well-defined transitions. These transitions, often depicted as arcs in a state diagram, are triggered by events and may involve guard conditions and actions.

UML offers various features to visualize the structure of a system, including timing marks, time expressions, and constraints. Active classes are used to monitor instances of the class, while threads and processes monitor the operations of a process.

State chart diagrams are particularly useful in describing the different states of a component within a system. They illustrate how events, both internal and external, affect the states of objects. Key elements in creating a state chart diagram involve identifying significant objects, defining their states, and describing the events that trigger state transitions.

## Events & Signals

**Events and signals are two key concepts in UML for modelling the dynamic behavior of systems.**

## **Events**

Events are occurrences that happen at a specific time and place. They can be internal (within the system) or external (outside the system) and are often modelled in UML as operations within an object's class definition. Internal events, also known as system events, occur within the system's boundaries, while external events originate outside the system.

- Events can be: internal or external, synchronous or asynchronous.
- Time (at which event executes) is an implicit attribute of events.
- Two events that are casually unrelated are called “concurrent events”.

A cashier pressing the "List of Items" button on a POS system represents an external event, while a sale object receiving a "list of items" message from another system component is considered an internal event.

**Signal Event**

 A **signal** is an asynchronous message sent from one object to another. A **signal event** occurs when a signal is sent or received. Each signal transmission is defined by a unique signal class, and every signal class has a unique name. For example, exceptions are modeled as signals in UML

- A signal event is used to send/receive a signal.
- A signal’s attribute serve as a parameter.
- A unique signal class defines all signal transmission.

**Call Event**

This event is a synchronous request from one object to another to perform an operation. The sender transmits a message and waits for a response from the receiver.

*Example,* a customer waits for the OTP during an online transaction.

![Untitled](Untitled%2060.png)

**Time Event**

This event happens at a specific time or after a certain amount of time has passed. For example, a time event could be used to model a system that disconnects a call after 15 seconds

**Change Event**

This event happens when a specific condition becomes true. For example, a change event could be used to model a system that stops charging a device when the time is 11:50 AM.

![Untitled](Untitled%2061.png)

### **Sending & Receiving Events**

At least two objects are involved in sending event and receiving events: the sender and the receiver. The sender sends a signal or call to the receiver, and the receiver may or may not respond. 

If the event is a synchronous call, the sender waits for the receiver to respond before continuing. 

If the event is an asynchronous signal, the sender does not wait for a response. In this case, the event might activate the receiver's state machine, invoke a method in the receiver, or be lost entirely.

## **Signals**

Signals are a specific type of event representing an asynchronous message transmitted from one object to another. In UML, signals are modelled by listing them in a dedicated row within the class representation. Each signal has instances, attributes, and relationships that perform various operations.

![Untitled](Untitled%2062.png)

**Event Handling**

Sending and receiving events involve two entities: a sender and a receiver.

- When a signal is sent, the sender continues processing without waiting for a response from the receiver. This asynchronous approach means the signal might be lost, trigger the receiver's state machine, or invoke a method within the receiver.
- In contrast, when an object calls an operation (synchronous), the sender and receiver are synchronized for the duration of the operation i.e.,  the sender waits for the receiver's response before continuing. The flow control of the sender is suspended by the receiver until the operation is either finished or terminated.

### Common Modelling Techniques for Signals

**Modelling a Signal Family**

Signals are frequently arranged hierarchically in event-driven systems. To construct a signal family model, 

1. You should identify all signal types receivable by a group of active objects. 
2. Group common signals into a hierarchy based on inheritance and generalization/specialization. 
3. Look for polymorphism and refine the hierarchy with intermediary abstract signals as needed.

**Example,** In a mobile phone system:

- A root signal "Mobile Signal" can be specialized into "Network" and "Hardware Fault" signals.
- The "Hardware Fault" signal can be further categorized into "Power Fault", "Data Fault", or "Backup Fault."

![Untitled](Untitled%2064.png)

**Modelling Exceptions**

A key aspect of modeling is defining and representing the exceptions that a class or interface's operations may throw. Modeling exceptions is the inverse of modeling a signal family because you begin with a general exception and define specialized exceptions that an object may raise.

*Understanding the differences between internal and external events, as well as the asynchronous nature of signals, is crucial for comprehending how UML models dynamic system behavior.*

## State Machines

State machines, are a powerful tool in UML for representing the dynamic behavior of objects, classes, use cases, and even entire systems. State machines are useful to modelling real-time or event driven systems because they show system’s dynamic behaviour.

A state machine diagram visually illustrates the sequence of states an object goes through during its lifetime, the events that trigger transitions between these states, and the actions resulting from those state changes.

### **Why Use State Machines?**

State machines are particularly well-suited for modeling real-time or event-driven systems where understanding dynamic behavior is crucial. They are beneficial during the software development process for:

- **Understanding Complex Behavior:** Illustrating intricate state changes in objects.
- **Modeling Object Lifespan:** Simulating an object's existence, particularly for classes, use case implementations, and overall systems.
- **Managing Multiple Control Flows:** Visualizing how concurrent processes within an object interact and change states.
- **Modeling Reactive Objects:** Representing the behavior of objects that respond to events, such as user interfaces, controllers, and embedded systems.

### Key Components of a State Machine

### **State**

A state represents a condition or situation during an object’s lifespan where it satisfies one condition, performs an action, or awaits an event. An object remains in a state for a finite duration.  Examples include "Waiting", "Processing", "Active", or "Idle".

A state has five key components:

1. **Name:** Distinct label to avoid ambiguity
2. **I/O Behaviour**: Actions or activities associated with entering or exiting the state.
3. **Internal Transitions:** Events handled within the state without causing a transition to a different state.
4. **Substates:** Nested states within a composite state, allowing for hierarchical representation of complex state behavior.
5. **Deferred Events:** Events that are not immediately processed in the current state but are instead postponed for handling in a later state

![Untitled](Untitled%2065.png)

The initial and final states are called **pseudo-states.** The **Initial State** is  default starting point of a state machine or substate, visually represented as a filled black circle. The **Final State** marks the completion of a state machine or an enclosed region within it, depicted as a filled black circle enclosed within an unfilled circle

## Transitions

**Transitions**, in the realm of UML state machines, represent the movement and transformation between different states within a system. They signify that an object, upon the occurrence of a specific event and the fulfillment of certain conditions, will shift from its current state to a designated target state.
A transition "fires" when the state change happens .

**Key Aspects of a transition**

- **Source State** The initial state from which the transition originates.
- **Event Trigger:** The stimulus or occurrence that has the potential to initiate the transition, prompting the object to move from the source state. These triggers can be signals, calls, or even the passage of time.
- **Guard Condition:** A Boolean expression, enclosed in square brackets and positioned after the event trigger, that dictates whether the transition should occur. The guard condition is evaluated only after the trigger event takes place.
- **Action:** A discrete, atomic computation executed during the transition. These actions can involve operations like sending signals, making calls, creating or deleting objects, or performing calculations. They represent the behavior exhibited by the object as it transitions between states.
- **Target State:** The final state that the object enters after the successful completion of the transition.

![Untitled](Untitled%2066.png)

**Transition Firing:** The actual moment of state change is referred to as 'firing.' When a transition fires, the actions specified for that transition are carried out, and the object's state is updated to the target state.

**Self-Transition:** In cases where the source and target states are the same, it's termed a self-transition. This signifies that the object remains in the same state even after the transition, typically performing some internal actions.

### **Advanced State Machine Concepts:**

- **Substates:** Allow for hierarchical decomposition of states, representing more granular behavior within a larger state. Substates can be sequential (one after another) or concurrent (happening in parallel).
- **History States:** Used within sequential substates to "remember" the last active substate before transitioning out of the composite state, allowing the system to resume from a previous point.
- **Composite States:** Encompass either concurrent (orthogonal) or sequential (disjoint) substates. For example, a "Playing" state in a video player might have concurrent substates for "Displaying Video" and "Outputting Audio".

## Processes and Threads

**Classes and Events:** 

An active class in UML represents an object that owns its own thread of execution, essentially meaning it operates independently and can initiate actions. This independent operation aligns with the concept of processes and threads in operating systems.

Active classes stand out because they possess a "flow of control," meaning they can initiate actions independently. In contrast, normal classes, termed passive classes, lack this inherent ability to control flow. They react to external stimuli but don't drive the system's behavior on their own.

Active classes, often representing threads or processes, embody the starting point of program execution or control flow. When an active object is created, its associated flow of control automatically initiates, ceasing only when the object is deleted.

**Flow of Control**

In concurrent systems, understanding the flow of control is crucial. While sequential programs have a single flow of control, concurrent systems have multiple flows happening simultaneously. UML active classes help visualize these interactions and dependencies between various flows within a system.

**Processes**

A process is a heavyweight, independent execution flow managed by the operating system. Processes have their own memory space and resources, allowing them to run in parallel with other processes. In UML, you can model a process as an active class stereotyped with "process".

A process communicates with another process using communication techniques like, signals, shared memory, semaphore files, etc. Processes are never nested within each other. 

**Threads**

A thread is a lightweight execution flow that exists within a process. Threads within the same process share the memory space and resources of that process. UML allows representing a thread as an active class stereotyped with "thread". Threads are not nested within each other.

**Communication**

When objects participate with another object by passing messages, this is called communication between objects. There are four possible communications of interaction with passive and active objects:

1. Passive to Passive Object:  A signal can be transferred from one inactive object to the next.
2. **Active to active object:** A message may be sent from one working object to the next using intercrosses correspondence.
3. **Active to passive object:** a message should be sent from an active object to an inactive object.
4. Passive to Active Object: A message can be transferred from a passive object to an active object.

**Synchronization**

A single process (and hence an object) can have multiple control flows, and different operations can have different control flows. But, in a single object there are always many control flows. The problem occurs when multiple control flows attempt to execute concurrently, they can interfere with each other and corrupt the object’s state if not properly managed. This is a classic problem of mutual exclusion in concurrent programming. 

A way to address this is to treat an object as a critical region and use synchronization mechanisms to ensure that only one control flow can enter the critical region at a time. There are three ways to implement this in object oriented architectures:

**Sequential:**  In this model, the object allows only one flow at a time, and the callers are synchronized outside the object. This is the simplest approach but may not be suitable for all situations.

**Guarded:** In this model, all calls to the object’s guarded operations are synchronised to ensure that only one operation can be invoked at a time, effectively reducing the object to sequential semantics. 

**Concurrent**:  This model involves synchronizing specific operations within the object to protect shared resources and ensure data consistency.

### **Modeling Processes and Threads in UML**

**Class Diagrams for Visualization**

Class diagrams effectively visualize the relationships between processes and threads. For instance, you can model:

- Multiple active classes representing independent processes, communicating with each other.
- An active class (representing a process) containing nested active classes (representing threads) within it, illustrating how threads operate within the context of a process.

**Interaction Diagrams for Communication**
Sequence and collaboration diagrams are valuable for depicting the communication between processes and threads. They illustrate the messages exchanged between them, whether synchronous (like procedure calls) or asynchronous (like message queuing).

**State Machine Diagrams for Behavior**
State machines can model the behavior of individual processes or threads. Orthogonal states within a state machine diagram can represent the concurrent execution of different parts of a process or thread.

**Synchronization**

UML provides mechanisms like guard conditions (in state machines) and constraints on operations to specify synchronization rules.

### **Modelling Multiple Flows of Control**

Using class and interaction diagrams to illustrate complex interactions between concurrent execution flows.

- **Identify Potential for Concurrent Interaction:** Begin by identifying areas within the system where multiple flows of control might interact concurrently.
- **Model Each Flow as an Active Class:** Represent each identified concurrent flow as a separate active class. An active class in UML encapsulates a thread or process, indicating an independent flow of control.
- **Design for Loose Coupling:** When designing these active classes, strive for loose coupling among them. This means ensuring each active class has a distinct responsibility and minimal dependencies on other active classes. This promotes modularity and maintainability within the system.
- **Define Clear Responsibilities and Communication:** Establish a well-defined separation of responsibilities among these active classes. Determine how these active classes will interact and communicate with each other and with passive objects in the system

Interaction diagrams help visualize the dynamic interactions between objects, pinpoint areas where synchronization is critical, and refine the understanding of concurrent behavior. Interaction diagrams, particularly sequence diagrams and state machines, should complement the class diagram in modeling multiple flows of control.

### **Modelling Inter-process Communication (IPC)**

When communicating across threads within the same process, objects can communicate via calls or signals. However, when communicating over the processes various structures could exist. The inter-process connectivity is compounded because processes can exist on different nodes in distributed networks. Inter-process communication might also be needed when integrating multiple control flows in the system. **Message Passing** and **Remote Procedure Calls (RPCs)** are  ****two popular methods of inter-process communication. 

Employing asynchronous communication (for message passing) and synchronous communication (for remote procedure calls) in interaction diagrams one can model inter-process communication.

In order to model inter-process communication, you can use following steps -

- **Model Multiple Control Flows:** Begin by modeling the multiple control flows present in the system. This involves identifying the active objects responsible for each flow and their interactions.
- **Identify Processes and Threads:** Determine the processes that will host these active objects and, if applicable, the threads operating within each process. Objects within the same thread can communicate via signals or call events (synchronous or asynchronous). However, communication between objects in different processes often requires different mechanisms.
- **Model Communication Mechanisms:** Two common techniques for inter-process communication: **message passing** and **Remote Procedure Calls (RPCs)**. In UML, these are often represented as synchronous and asynchronous communication, respectively. Use asynchronous communication (e.g., sending messages) to depict message passing between processes, and synchronous communication (e.g., procedure calls) to represent RPCs.
- **Specify Communication Details:** To enhance clarity, specify the exact communication mechanism employed using notes or collaborations within the UML diagram. This could involve indicating the use of specific technologies like message queues or protocols. For example, a note could mention "Communication via Java Beans messaging service" or "Interaction through CORBA ORB."

## Statechart Diagrams in UML

Statechart diagrams visually represent the dynamic behavior of a system by illustrating the different states an element can assume and the transitions between those states. Events (Internal/External) control these states. They prove particularly valuable when modeling reactive systems – systems that respond to internal or external events.

A statechart diagram is nothing more than a schematic representation of a state machine.

### **Purpose and Applications**

The sources emphasize the following key purposes of Statechart diagrams:

- **Modeling System Dynamics:** They depict the flow of control within a system, capturing how events trigger changes in an element's state.
- **Modeling Reactive Systems:** They effectively illustrate the lifecycle of reactive systems, highlighting how these systems respond to events.
- **Object Lifecycle Visualization:** They visually communicate the various states an object traverses throughout its existence, from creation to termination.
- Several common applications of Statechart diagrams:
    - **Modeling System Object States**
    - **Modeling Reactive Systems and their components**
    - **Identifying Events Leading to State Changes**
    - **Reverse and Forward Engineering**

**Key Elements and Concepts**

The sources break down the core elements and concepts integral to Statechart diagrams:

- **State:** A condition or situation during an object's lifespan where it satisfies certain conditions, performs actions, or awaits events.
- **State Machine:** A model capturing an object's states and the transitions between them, driven by events and conditions.
- **Transition:** A relationship connecting two states, signifying that an object in the first state will enter the second state upon the occurrence of a specific event and fulfillment of any associated conditions.
- **Event:** An occurrence that may trigger a state transition. The sources categorize events as:
    - **Signal Event:** The receipt of an asynchronous signal.
    - **Call Event:** A synchronous operation invocation.
    - **Time Event:** The passage of a specified time interval (e.g., "after(10 seconds)").
    - **Change Event:** A change in a particular condition (e.g., "when (temperature > 100)").
- **Guard Condition:** A Boolean expression that must evaluate to "true" for a transition to occur.
- **Action:** An executable behavior associated with a transition.
- **Entry Action:** An action executed upon entering a state.
- **Exit Action:** An action executed upon exiting a state.
- **Internal Transition:** An event handled within a state without exiting that state.
- **Composite State:** A state containing nested substates, either sequential or concurrent.
- **History State:** A composite state that "remembers" the last active substate before transitioning out of the composite state.

### **Drawing a Statechart Diagram**

The sources outline a structured approach to creating Statechart diagrams:

1. **Identify Significant Objects:** Determine the objects whose states require modeling.
2. **Define States:** Clearly define the distinct states each object can assume.
3. **Describe Events:** Identify the events that trigger transitions between states.
